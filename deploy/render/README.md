# Render deployment (free tier)

A second deployment running alongside the Oracle VM. [`render.yaml`](../../render.yaml) at the repo root is a Render
Blueprint that builds the existing Dockerfiles (repo root as context) as three **free web services** in Frankfurt:

| Service | Dockerfile | Notes |
| ------- | ---------- | ----- |
| `aviation-api` | `api-service/Dockerfile` | GraphQL + REST; pings producer and worker (`WAKE_URLS`) |
| `aviation-producer` | `adsb-producer/Dockerfile` | public, so `/ingestion/live/*` needs `PRODUCER_TOKEN` |
| `aviation-worker` | `telemetry-worker/Dockerfile` | answers `/health` on `$PORT` so Render can run it as a web service |

MongoDB Atlas and CloudAMQP are the **same** as the VM's. Nothing under `deploy/` or the GHCR workflow changes.

## Free-tier behaviour

- **Sleep:** a free service sleeps after 15 minutes without inbound HTTP and takes ~30–60 s to wake. The api pings
  `WAKE_URLS` on startup and every 10 minutes, so opening the frontend (or GraphiQL) wakes the whole stack, and it
  all sleeps ~15–30 minutes after the last request. The first request after a sleep is slow, and a
  `trackableAircraft`/`startTracking` call can fail with "producer unavailable" until the producer is up; retry.
- **Hours:** 750 free instance-hours a month for the whole workspace. Three services running 24/7 would need ~2190,
  so don't add an external uptime pinger.
- **Tracking state** lives in the producer's memory and is lost when it sleeps or redeploys. Aircraft in
  `ADSB_PRODUCER_AIRCRAFT` are tracked again on every wake.
- **Shared broker and database:** the VM and Render workers share the `telemetry.ingest` queue (each message is stored
  once) and each api gets its own `telemetry.live` queue, so both see every live update. **Only one producer should
  track a given aircraft** (VM or Render), otherwise ADSB.lol is polled twice and duplicate points are stored. Set
  `ADSB_PRODUCER_AIRCRAFT` on one side only.
- 512 MB / 0.1 CPU per service. Tracing is off (`OTEL_ENABLED=false`); to trace, set the Grafana Cloud variables from
  the main README on each service.

## Credentials

Nothing Render-specific goes in the repo, `.env` or GitHub secrets. What the deployment needs:

| What | Where it lives | Needed? |
| ---- | -------------- | ------- |
| Render account linked to GitHub (Render GitHub app with access to this repo) | Render dashboard, one-time | yes, so Render can clone and build |
| `MONGODB_URI` (Atlas user and password) | Render env vars, api + worker | yes |
| `RABBITMQ_URL` (CloudAMQP user, password, vhost) | Render env vars, all three services | yes |
| `API_TOKEN`, `ADMIN_TOKEN` | Render env vars, api | yes (same values as the VM) |
| `PRODUCER_TOKEN` | generated by Render in the `aviation-shared` group | automatic |
| Render API key / deploy hook | nowhere | no: `autoDeployTrigger: checksPass` deploys without GitHub Actions calling Render |
| GHCR / registry credentials | nowhere | no: Render builds from the repo's Dockerfiles, not the GHCR images |

Never put these values in `render.yaml`, which is committed: `sync: false` makes Render ask for them in the dashboard,
and they stay there. To rotate one, edit it under the service's **Environment** tab (this redeploys the service).

## Setup

1. **Atlas → Network Access:** allow `0.0.0.0/0` (Render free services have no static outbound IPs). Use a strong
   database user password.
2. **Render dashboard → New → Blueprint**, pick this repository and branch `main`. Render reads `render.yaml`.
3. Fill in the `sync: false` values (use the same values as the VM's `/opt/aviation/.env`):

   | Service | Variable | Value |
   | ------- | -------- | ----- |
   | api, worker | `MONGODB_URI` | Atlas connection string |
   | all three | `RABBITMQ_URL` | CloudAMQP `amqps://` URL |
   | api | `API_TOKEN`, `ADMIN_TOKEN` | same as the VM (the frontend already uses `API_TOKEN`) |
   | api | `PRODUCER_URL` | `https://aviation-producer.onrender.com` (the producer's URL shown by Render) |
   | api | `WAKE_URLS` | `https://aviation-producer.onrender.com/health,https://aviation-worker.onrender.com/health` |
   | producer | `ADSB_PRODUCER_AIRCRAFT` | empty, or e.g. `*` if Render (not the VM) should track |

   `PRODUCER_TOKEN` is generated once in the `aviation-shared` environment group and used by api and producer.
   If Render gives a service a different `onrender.com` name, update `PRODUCER_URL`/`WAKE_URLS` to match.
4. Apply. The first build takes a few minutes per service. No seeding is needed: the database is shared.
5. Point the frontend (or a second frontend build) at `https://aviation-api.onrender.com/graphql` and
   `wss://aviation-api.onrender.com/graphql` for subscriptions.

Deploys: `autoDeployTrigger: checksPass` redeploys a service on every push to `main` once the GitHub `deploy` workflow's
checks pass, and only when its folder, `shared/`, `pyproject.toml` or `uv.lock` changed. Manual redeploys and
rollbacks are in each service's **Events** tab.

## Check

```sh
API=https://aviation-api.onrender.com
curl $API/health
curl https://aviation-producer.onrender.com/health
curl https://aviation-worker.onrender.com/health          # {"status":"ok","rabbitmq":true}
curl https://aviation-producer.onrender.com/ingestion/live/status/%2A   # 401 without the producer token
E2E_API_URL=$API E2E_API_TOKEN=... uv run pytest -m e2e
```
